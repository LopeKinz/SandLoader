Mods for Sandustry, without rewriting a file of it.

A mod loader with an in-game console, a mod manager, and support for existing Fluxloader mods. Patching happens in memory while the game loads, so no file's content is ever modified and a game update cannot leave a broken patched file behind. Uninstalling is one command.

Why it is built this way

A mod loader that cannot break your install

Every design decision follows from one constraint: nothing may be written into the game directory. What that buys you is below.

Verification stays green

Patches are applied to bytes in flight, never on disk. Steam's file check sees an untouched install, because it is one.

Anchored on source, not offsets

Hooks match authored string literals like "game:ready" — never module ids or minified names, which change on every build.

Fails safe, never halfway

A failed required patch aborts and serves the file untouched. A broken loader must not become a broken game.

A real in-game console

Spawn any material, set resources, control the simulation, inspect the live modding API — with completion and history.

Fluxloader mods, unmodified

Reads their manifest, runs all three entrypoints, provides fluxloaderAPI, and bridges their content onto the registries this build actually has.

Permissions you can withdraw

Reviewed before a single line of mod code is read — and revocable afterwards from the manager, not just at install time.

One hook

The whole modding API, already in the game

Sandustry ships a complete internal API — the object its bundle calls FH, with 79 namespaces. It is simply never published to window.

So SandLoader reimplements none of it. A single patch captures the game's own object at the moment it announces readiness, and from then on SandLoader.game is FH.

js/bundle.js — patched in memory
// the game's own readiness announcement
FH.events.emit(state, "game:ready", { state })

// one anchor, and every namespace follows
events    elements  ui        structures
storage   sprites   workers   effects
world     terrains  input     sound
items     rendering config    player
i18n      upgrades  tools     energy   …

Documentation

Everything needed to install SandLoader, use it, and write mods for it. Verified against Sandustry 0.5.6.

Requirements

There is no file we are allowed to add and no non-destructive way in, so the installer says so plainly rather than offering a workaround that would modify game files.

If you are on the modded branch

Switch back before installing: right-click Sandustry in your Steam library → Properties → Betas → select None, and let Steam re-download. You can confirm which branch you are on from appmanifest_2764460.acf, where BetaKey reads public on vanilla.

Installing on the experimental branch is not blocked, but nothing about it is verified: anchors may not resolve, and the loader will report what failed rather than pretend.

    git clone https://github.com/LopeKinz/SandLoader.git
cd SandLoader

  2. Check Node

    node --version      # must print v18.x or higher

  3. Run the installer

    It detects your build and picks the right attach point on its own.

On GOG and standalone

SandLoader adds three files beside the untouched app.asar and names each one. Electron already searches resources/ for app before app.asar, so the added directory loads first and hands control straight back to the real game.

Update & uninstall

Editing SandLoader's own code needs no reinstall — just restart the game. To remove it entirely:

node install.js --uninstall

That puts the install back exactly as it was found: on a build with a loader slot the slot directory goes, and on 0.5.6 the two renamed paths get their names back. node install.js --repair puts a half-applied or orphaned attach right and says what it found. To see what is currently installed, on what evidence:

node install.js --status

Managing mods

Main menu → SandLoader Mods to install, enable, or remove mods. Details on any row shows what that mod can reach, and lets you approve or withdraw those permissions afterwards.

Install from Workshop

Takes a Workshop URL or a bare id. An item you are already subscribed to is found locally instead of downloaded; anything else goes through SteamCMD, which the installer fetches from Valve on first use. A Workshop mod is copied out into your local mods folder rather than loaded in place, so Steam still owns its content and SandLoader never deletes it.

Scanned before they run

Mod sources are read for the Sandkit namespaces they call and checked against what this build actually offers — statically, so calls on code paths that never execute are still seen. A mod needing a namespace this build lacks is flagged before you enable it, rather than throwing in a tooltip an hour later.

Custom maps

Main menu → Maps opens SandLoader's own browser: every .custommap the game can see, a preview of whichever one is selected, and a Play button. The game has a custom-maps screen of its own in this build, but its load action only shows a “coming soon” panel, so this is not overriding something that already worked.

Two kinds of map share one folder, and each row says which it is: a map mod's, written by SandLoader, and the player's own — saved by the game, or brought in with Import map… from anywhere on disk.

The support was there all along

The game reads .custommap files from custom_maps under its user-data folder, and the four IPC handlers that save, load, list and delete them sit outside the build's MODDING_ENABLED gate. Nothing had to be added to the game and nothing had to be patched into it. What was missing was anything that wrote the file.

What a .custommap is

Two lines. The first is metadata — id, name, seed, recorded size. The second is the whole document, carrying six layers, each one {width, height, dataUrl} with a base64 PNG in the data URL. The game's own save routine writes it that way and its two readers split on exactly that boundary, so a file written as a single JSON object lists perfectly and then fails the moment it is opened.

LayerWhat the game does with it
terrainOne pixel is one world cell. RGB is looked up in a palette to decide what that cell is made of, and the world's size is this image's size — there is no scaling step.
lightsEvery pixel that is not transparent becomes a point light on that cell, coloured by its own RGB.
lightsMetaA per-pixel override for the light at the same coordinate: its brightness and its size.
sensorsArtifact markers.
authorizationA per-cell restriction zone — no jetpack, no grabbing, no building, no digging, and the combinations of those.
wallThe cosmetic backdrop drawn behind the world. Collision never reads it.

All six are mandatory. The game's loader awaits all six at once with no undefined-guard, so a file missing one does not lose that layer — it fails to load at all, with a generic TypeError and no friendly message. A blank stand-in would be a guess about what an invented layer means to the game, so SandLoader refuses an incomplete set rather than padding it.

A map that ships with a mod

A mod names its six blueprints in its manifest; SandLoader assembles them into the file the game already reads and writes it straight into custom_maps. There is no separate map format to learn and no packaging step.

{
  "id": "canyon",
  "name": "Canyon",
  "version": "1.0.0",
  "map": {
    "blueprints": {
      "terrain":       "map/terrain.png",
      "lights":        "map/lights.png",
      "lightsMeta":    "map/lights-meta.png",
      "sensors":       "map/sensors.png",
      "authorization": "map/zones.png",
      "wall":          "map/wall.png"
    }
  }
}

The map appears in the browser tagged Mod, under the mod's own name, and leaves with the mod when it is disabled or removed.

Only files SandLoader wrote are ever pruned

A mod's map is named smln.<modId>.custommap, and pruning considers nothing else — the player's own maps live in the same folder and are not ours to remove. An imported map is therefore deliberately renamed if its name would look like one of ours: a file called smln.custommap would otherwise be deleted on the next launch, as the leftover map of a mod that is no longer installed. The id inside the file is rewritten to match, because the game opens a map by asking for <id>.custommap and a file whose name and id disagree lists perfectly and then fails the moment it is started.

The flight ceiling scales with the map

The game refuses to let the player hover inside a fixed 600-pixel strip at the top of the world, and puts a collision ceiling at 550. Both numbers were chosen for the vanilla world, which is 3840 cells — 15,360 pixels — tall, where 600 pixels is a 3.9% band across the top. Neither number scales. On a custom map they are the same two absolutes, so a 320×240 map had 62.5% of its height as a no-fly zone.

SandLoader scales the strip to the map's own height, keeping the proportion the vanilla world has. A map at least as tall as the vanilla world keeps the game's own numbers untouched.

Measured in the running game

That same 320×240 map goes from 62.5% to 3.9%, and a player hovers where the game previously refused.

A map reloaded from a save gets the vanilla ceiling

Whether a world is a custom map is read from custom_map= in the game's own URL, which is the only record of it — the state carries no marker for it anywhere. A custom map saved and reloaded through the game's save system comes back under load= instead, and there is no state-side signal to tell it apart from the vanilla world, so it gets the vanilla ceiling back. Documented, not fixed: fixing it properly needs a marker written into the save.

The map editor

Create a map from nothing at a size you choose, paint it, check it, save it, play it — all inside the game, with no external tool and no file to hand-assemble. It opens from the same Maps browser: New map… in its footer, or Edit beside Play on a map that already exists.

The size floor is 158 × 201 cells

Not a preference and not a round number. The game drops the player at one fixed position and never looks to see what is there:

// the branch a .custommap always takes
x = (widthInCells / 2) * cellSize + 315   // half the width, plus about 79 cells across
y = 200 * cellSize                     // row 200, whatever the map's height

There is no scan for open ground, no fallback and no second attempt. A map narrower than 158 cells puts that x past its own right edge; a map shorter than 201 cells has no row 200 at all. Either way the player starts outside the world. So the editor will not create a document below that size, the resize dialog refuses one, and the validator reports it as an error rather than a suggestion. There is no way to move the spawn.

The ceiling is total cells, not cells per axis

The game's own per-axis limit is 16,383 cells, because a shared mouse position is carried in a Uint16 of world pixels and anything past that wraps around — clicks, digging and building would all land somewhere other than where the player aimed. But both axes at that limit at once would be 268 million cells, which is not a map anything can hold. A per-axis rule is the wrong shape for the real constraint.

Measured, not estimated

8000×4000 — 32 million cells — opened in 5.0 s and saved a 4.4 MB file, while driving the renderer to 1.78 GB with a 3.08 GB peak. The editor caps at half of that: 16 million cells, however they are shaped.

Both size dialogs show a live memory figure while a size is being typed — about 34 bytes a cell, measured against a 1162 MB baseline — so what a size will cost is visible before it is committed rather than discovered afterwards. A refused size says so, and says which of the two rules refused it.

The palette says what the player gets, not what the colour is called

This exists because a test map built from two colours the format documents came out unplayable, and neither colour did what its name suggested.

ColourReads likeWhat the player actually gets
102,102,102background rockFog — the sealed-pocket material. The palette entry really does say {bg: Stone, fg: Fog}, but the terrain resolver reads only .fg and throws the rest away, so no background stone is ever placed. Fog is solid on load; break a single cell of it and an unbounded flood fill walks every connected fog cell and turns the whole mass to open air.
34,34,34dark stoneBedrock — solid, collidable and permanently un-minable. It carries no hit points, so the game's own destructibility test is false for it and no tool ever damages it.

So every row in the picker is labelled by outcome: Solid rock (needs a drill), Bedrock (permanent floor), Crackstone (needs dynamite), Open air. Every fog row says “blocks until dug” in its label and not only in its note, so nobody scanning the list for air can reach for one blind.

Alpha 0 is not air either

A fully transparent terrain pixel does not resolve to empty space — it decodes to Fog, the same collidable, flooding material. Every terrain pixel must be opaque. So the eraser writes the palette's real empty colour rather than clearing to transparency, a blank document starts full of that colour rather than blank, and a see-through pixel is an error at save time, not a warning.

Six layers, six different surfaces

The same bytes mean different things in different layers: a colour that is solid rock in terrain is a brightness and a size in lightsMeta. Offering the terrain palette whatever layer was selected meant an author could pick a rock colour and write a number they never typed and could not see. So each layer gets the surface its own decoder deserves.

LayerSurfaceWhy that one
terrainthe paletteA fixed table of the colours the resolver recognises, labelled by what each one gives the player.
lightsa colour pickerThe pixel's RGB is the light's colour, straight through. Any colour is legitimate, so there is no table to offer.
lightsMetatwo numeric fieldsIt is two numbers wearing a colour's clothes: R is brightness × 100, G is size ÷ 4, B is unused. A zero means “keep the default”, not zero — the decoder tests each channel before it uses it.
sensorstwo entriesOnly pure red and pure yellow mean anything. Every other opaque colour silently becomes Artifact 1, so two entries is the honest surface and anything else is reported.
authorizationtwelve numbered zonesEach one labelled by what it forbids rather than by its number. An unrecognised colour is zone 0, which restricts nothing at all.
walla free colour, with a countA live count of distinct colours against the 254-value ceiling that layer's palette has room for.
Two things here are unverified, and the interface says so

The wall layer's encoding. Its decoder was never found. The editor offers a free colour and the 254 count, and invents no semantics for what those colours look like. If someone reads that decoder, this is the paragraph that changes.

The 1.1× brightness special case. The lights decoder singles out 58,211,204 and raises that light's brightness to 1.1. The interface states it; nobody has confirmed the game honours it in play.

Tools, transforms, and what a save refuses

Brush, eraser, fill, line, box and eyedropper, with undo and redo over all of them. Resize, crop, mirror and shift run on all six layers together, as one undo step, because the six have to stay the same size as each other: a layer whose size disagrees with the terrain layer is read at the wrong offset from the second row onward, so what was drawn on it slides further sideways with every row down the map, smearing diagonally across the world without a word of complaint. The spawn cell — the one thing in the world an author cannot see and cannot move — is drawn on the canvas as a marker.

Before a save, the map is checked against rules written for a mapmaker rather than for a debugger. Each names something the player will experience, in the words someone holding a brush would use, because none of it is visible until a map is loaded.

Errors — the map will not playWarnings — it will play and disappoint
No terrain layer; a size the game cannot carry; layers that disagree about how big the world is; a recorded size that does not match the terrain layer; see-through terrain pixels; a colour that makes the game abandon the map on load; a spawn outside the world; more wall colours than the backdrop's palette can hold. A spawn buried in solid rock; fog the author may not have meant, with the size of its largest connected patch; a terrain layer that is all one colour, or has nothing solid in it at all; artifact and zone colours that will silently become something else; light settings with no light underneath them.
Errors block a save; warnings do not

A map that will not open is refused. A map that will open and disappoint is reported and then saved anyway — the author is the one who knows whether a wall of fog is a mistake or the whole point of the map.

Achievements

Sandustry refuses to unlock achievements on a save that has been cheated on or modded. That is the game's own rule, in its own code:

function unlockAchievement(state, id) {
  if (state.store.integrity?.cheatsUsed || state.store.integrity?.modsUsed
      || config.debug.active || state.session.cinematic) return   // blocked
  ...
}

SandLoader respects that by default. Any console command that changes your world or your resources marks the save, and says so in its reply:

> give gold 1000
gold  gold: 0 -> 1000 (save marked: achievements now disabled)

You can opt out. The choice is stored inside that savegame, so it travels with it.

integrity statusShow the current policy and whether this save is marked
integrity offStop marking the save when you cheat
integrity onResume marking (the default)

Permissions

Sandustry's window runs with Electron's modern defaults — contextIsolation: true, nodeIntegration: false. Renderer and worker mod code therefore has no require, no process and no Buffer. That boundary is enforced by Chromium, not by SandLoader.

TierRuns inReaches
SANDBOXEDrenderer / workergame API, worker API, config, private storage
ELEVATEDrenderer / workerthe above, plus network and/or a wider filesystem root
NATIVEElectron main processreal Node.js — everything the game itself can
  • mods never receive the game's window.electron bridge or SandLoader's own SMLN.callMain RPC;
  • SMLN.net and SMLN.fs are gated on declared permissions — a mod without them gets a rejection, not a missing function;
  • every mod gets a private storage directory that traversal, absolute paths, UNC paths, device names and symlink escapes cannot leave;
  • the permission review happens before any mod code is read, required or evaluated.
Stated plainly

A mod declaring node gets a real require, from which fs, net, http and child_process are one line away. SandLoader therefore does not claim that filesystem and network restrict a native mod. They cannot, the capability reports enforceable: false, and the mod manager says so in plain language. Native mods are supported on purpose — they are just labelled.

vm is not treated as a security boundary anywhere in this codebase, because it is not one when the sandbox object carries require.

Making mods

A mod is a folder with a manifest. No build step, no dependencies, no boilerplate — a single file is a valid mod, and editing it needs only a restart. Built for Sandustry's vanilla branch; the experimental modded branch is not supported.

Your first mod

Create mods/hello/ with two files. That is the entire setup.

mods/hello/smln.mod.json

{
  "id": "hello",
  "name": "Hello",
  "version": "1.0.0",
  "renderer": "renderer.js"
}

mods/hello/renderer.js

SMLN.registerCommand({
  name: 'hello',
  summary: 'Say hello',
  args: [{ name: 'who', optional: true }],
  run: (args) =>
    ['hello, ' + (args[0] || 'world')],
})

Restart the game, open the console with ^, type hello. Done.

No reinstall loop

Editing a renderer file and restarting the game is the whole iteration cycle. With hot reload enabled you do not even restart — the mod is disposed and re-injected while the game keeps running.

Anatomy of a mod

A mod can have up to three halves, each running somewhere different. Most mods only ever need the first.

# a fully-equipped mod
mods/my-mod/the folder you create
├─smln.mod.jsonthe manifest — the only required file
├─renderer.jsruns in the game page, next to the console
├─worker.jsruns inside the simulation threads
├─main.jsruns in the Electron main process (privileged)
├─assets/sprites and other files you ship
└─locales/en.json, de.json …
1
The manifest is read and reviewed Permissions are resolved before any of your code is read or evaluated.
2
Patches are applied in memory Yours and SandLoader's are merged, conflict-checked, then the bundle is served.
3
Your renderer script runs Before any game code, with SMLN already installed.
4
The game becomes ready SMLN.whenReady() fires and the game's own API is captured.

The renderer half

Runs in the game page with SMLN already installed, before any game code. A throwing renderer script is caught and logged — it cannot stop the game from booting, or stop other mods from loading.

// 1 — runs immediately, before the game exists
SMLN.log('info', 'hello mod loading')

// 2 — runs once the game is up
SMLN.whenReady((api) => {
  api.game     // the game's own API
  api.state    // live game state
})

// 3 — every scene load re-runs this
SMLN.on('ready', (api) => {
  /* ... */
})

// 4 — clean up after yourself
SMLN.onDispose(() => {
  /* listeners, timers, patches */
})
  1. Top-level code runs first. The game does not exist yet, so SMLN.game and SMLN.state are still null. Use this for registration only.
  2. whenReady fires once the game is up — and fires immediately if it already is, so you never miss it by registering late.
  3. 'ready' fires on every scene load. Treat your script as an entry point that may run more than once.
  4. onDispose is what makes hot reload work. Give back what you took and your mod reloads without a restart.

The main-process half

A main entrypoint is a CommonJS module in the Electron main process with real Node. It is privileged — declaring it makes your mod NATIVE, and the installer says so before anyone enables it.

main.js

// Called once, in the Electron main process.
// Return { patches } to contribute bundle patches.
module.exports = {
  setup(ctx) {
    ctx.logger.info('native half up')
    return {
      patches: [ /* see below */ ],
    }
  },
}

What ctx carries

ctx.mod          // your manifest
ctx.capability   // resolved tier
ctx.logger       // namespaced to your id

Exporting a bare function works too — it is treated as setup. A patches array exported directly is also picked up.

Only when you actually need it

Renderer and worker code runs behind Chromium's own boundary — no require, no process, no Buffer. That is a real guarantee. A main entrypoint gives it all up, so add one only when the mod genuinely needs the filesystem, a socket or a subprocess.

Console commands

Commands get completion, history and argument hints for free. Return an array of strings and each becomes a line in the console.

SMLN.registerCommand({
  name: 'flood',
  summary: 'Fill an area with a material',
  args: [
    { name: 'material', values: () => SMLN.enums.ELEMENT_KEYS },  // tab-completes
    { name: 'radius', optional: true },
  ],
  run(args) {
    if (!SMLN.state) return ['no game loaded']     // say why, always
    const r = Number(args[1] || 3)
    // ... do the work ...
    return [`flooded r=${r} with ${args[0]}`]
  },
})

Missions & story

A mod can put objectives into the game's mission panel and beats into its story chain. Neither table has a registry API — they are module-scope literals the game assumes it is the only writer of — so the SDK's whole job is to put a mod's entry in, keep it there, and supply the four things the game does not: running the predicate, remembering the completion, keeping ids apart, and refusing content whose mod is absent.

The surface is scoped per mod: SMLN.forMod(id).story. Inside a renderer mod SMLN is that facade, so SMLN.story is the whole thing. A commented, loadable version of the example below — with all three cross-mod mechanisms and a console command to watch it work — ships as mods/example-missions/.

SMLN.story.speaker('surveyor', { name: 'MARA', portrait: PORTRAIT, color: '#8ec5ff' })

SMLN.story.objective({
  id: 'first-quota',                            // registers as <modId>:first-quota
  title: 'Fill the survey quota',
  description: 'Hold 250 gold at one time.',
  check: function (state) { return state.store.resources.gold >= 250 },
})

SMLN.story.step({
  id: 'briefing',
  after: 'establish_wet_sand_processing',      // a bare vanilla id means the game's own
  messages: [
    { speaker: 'surveyor', text: 'Core sample says this seam runs deep.' },
    { speaker: 'zoe', text: 'File it once the sand is moving.', showObjective: true },
  ],
  completeWhen: { objective: 'first-quota' },
})

The surface

CallDoes

story.complete(id) · story.isComplete(id)Complete an objective, or ask whether it is done.

A registration returns true for accepted — or queued until the game exists — and false for refused, always with a named error carrying the mod id and a code (E_STORY_BAD_ID, E_STORY_MISSING_DEPENDENCY, E_STORY_DUPLICATE_ID, E_STORY_NO_PORTRAIT, …). It goes to the log and to the in-game Problems panel, because a refusal only a log file ever sees is invisible to exactly the person it is for. Nothing here throws at a mod — a bad definition must not abort the mod that wrote it.

Ids are namespaced, always

objective({ id: 'first-quota' }) from example-missions registers as example-missions:first-quota. Two mods cannot collide in a table the game believes it owns alone, the author of a broken objective is in the log line without a lookup, and a cross-mod reference has to name the mod it means. Vanilla ids stay bare: find_fluxite means the game's own and cannot be shadowed, and writing a : into a registration id is refused, because that is the one way a mod could aim at another namespace by hand.

Reaching across mods

Three ways, in increasing order of coupling.

WriteReach for it when
requires: ['gas-pipes']The content makes no sense without the other mod. Absent or disabled, it is not registered at all and the log names both mods. Per registration — your mod itself still loads.
completeWhen: { objective: 'other.mod:their-goal' }The two pieces genuinely belong to one chain. after and next take a namespaced id the same way. A reference nothing ever registers is reported once, by name, instead of waited on forever.
story.emit('reactor-online')The emitting mod should not have to know who is listening. It publishes <modId>:reactor-online; anyone finishes on completeWhen: { event: 'my.mod:reactor-online' }. This is what lets a mission pack ship for a machine mod that has never heard of it.

Ordering is by declaration, never by load order: a step naming an after that has not registered yet waits for it, and the queue is retried until it stops moving. After five ticks the reference is declared missing, reported once by name, and the step is appended to the end rather than dropped — load order is not something a mod author can control, so it must not be something they have to reason about.

Why SandLoader ticks the predicates

check is a field the game already has, and its evaluator is generic — but that evaluator fires at only three event sites, and seven of the twelve shipped objectives are completed by hard-coded calls elsewhere. A mod's predicate left in the game's table would sit there unevaluated forever. So the SDK keeps the predicate and ticks it about once a second, deliberately not per frame, because a mod's predicate must not become a cost the simulation pays.

A mod's check is therefore never written into the game's table: the shipped evaluator does not catch, so a predicate left there would throw inside the game's own tech-unlock handler. Inside the SDK it is wrapped — a throw is logged against the mod that wrote it, and after three throws that one predicate is switched off and reported rather than throwing every second for the rest of the session.

Why completion is recorded separately

The game deletes a completed objective from store.objectives.active about five seconds later, and again at world load, and keeps no completed set anywhere at all. Left to that, a mod's objective would un-complete itself. That deletion is left strictly alone — it is the game's behaviour. Instead the SDK keeps its own record in the saved half of the state, under store.smlnStory, re-read whenever the state or its store is replaced, which is what a world load looks like from here. It is re-read as a replacement and never as a union: two saves have two different sets of finished missions, and carrying one into the other would hand a player completions they never earned.

Unloading a mod takes its objectives out of the game's table and out of the active list — an id left active in a save whose mod is gone is permanent, because the game refuses to complete an id its table no longer defines. The saved record is deliberately kept: turning a mod off and on again must not mean replaying its missions.

Measured in the running game

A mod's objective completed 1016 ms after its predicate turned true, and unloading the mod returned the game's table to exactly its twelve vanilla entries.

The story half is only half proven

Speakers and steps do register into the game's own live tables, a step inserts at the position it names with the chain intact, and a mod's speaker sits beside the vanilla two. Not verified: a dialogue beat actually appearing on screen, and a data: URL portrait actually rendering. Reaching a mod's beat needs play up to a factory rank, which nobody has done yet. Treat the pixels as unproven until someone has watched them.

Patching the game

Your mod can use the same anchor-based patch engine SandLoader uses for itself. Patches are contributed from the main-process half — return them from setup(), or export a patches array. Match an authored string literal, never an offset or a minified name.

Do
{
  id: 'my-mod-ready-hook',
  description: 'why this exists',
  find: /"game:ready"/g,
  replace: (m) => m,
  expect: 1,
  required: true,
}
Anchored on a literal the authors wrote. Survives reminification, and expect makes ambiguity an error instead of corruption.
Don't
{
  id: 'my-mod-ready-hook',
  find: /ie\.FH\.events\.emit\(p,/g,
  replace: '...',
}
ie and p are minifier output. They changed between 0.5.4 and 0.5.5, and will change again on the next build.

How to make my mod compatible

The single biggest source of broken mods is the Sandkit generation split. Sandustry's modding API exists in two shapes, and a mod written against the wrong one fails at the moment that code path runs — often long after startup, in a tooltip or on a button press. From a player's side that is indistinguishable from a mod that does nothing.

This section is how to not be that mod.

0. Target the vanilla branch

Before any API question: SandLoader supports Sandustry's vanilla (public) branch only. The experimental modded branch ships a different Sandkit generation, and nothing here is verified against it.

This is the whole reason the generation split exists

The modded branch ships Sandkit v1; vanilla ships the legacy surface. A mod written on the modded branch and shipped to vanilla players is the single most common way a mod arrives broken.

  • Develop on vanilla. If you build against the modded branch you are testing an API your players do not have.
  • Write v1 names anyway — see below. SandLoader translates them onto vanilla, so you get the forward-compatible spelling without needing the other branch.
  • Never assume a v1-only namespace exists. api.structures.recipes is the classic case: present on the modded branch, absent on vanilla.

1. Write against v1 names, always

The two generations name the same calls differently:

v1 — write this
api.elements.createAtCellWhenIdle(x, y, t)
api.elements.getTypeFromId('copper')
api.structures.isTypeAtCell(x, y, 'pump')
api.player.getWorldPosition()
SandLoader presents v1 names on both generations, binding the live state for you on legacy builds.
legacy — don't
api.elements.createAt(state, x, y, t)
api.elements.getElementTypeFromId(state, 'copper')
api.structures.isTypeAt(state, x, y, 'pump')
api.player.getPosition(state)
State-first and older names. Works only on 0.5.x, and breaks the day the game ships v1.

SandLoader translates 91 renamed calls across 17 namespaces, every target verified present in the shipped bundle. Write the v1 name and the adapter does the rest.

91calls translated
17namespaces covered
2generations, one API

2. Feature-detect anything that might not exist

The adapter can rename a call. It cannot invent a namespace this build does not have — and what exists moves between builds in both directions. api.structures.recipes did not exist at all before 0.5.6, which added it; upgrades still have no registration function anywhere in the bundle.

Do
if (api.effects?.createLightAtWorld) {
  api.effects.createLightAtWorld(x, y, opts)
} else {
  SMLN.log('info', 'no lights on this build')
}
Degrades to a working mod with one feature missing.
Don't
api.effects.createLightAtWorld(x, y, opts)
// throws on a build without effects,
// taking the rest of your tick with it
One missing namespace kills every line after it.

3. Check what the scanner will say about you

Before a mod runs, SandLoader reads its source for the Sandkit namespaces it calls and compares them against what this build actually offers — statically, so calls on code paths that never execute are still seen. That is deliberate: running the mod to find out would defeat the purpose.

The mod manager shows the result on your mod's row before anyone enables it:

SandLoader Mods → my-mod
API check   needs effects, tech.registerNode
             this build does not provide them

The scan reads two levels deep, so api.player.buildings.unlockByType is checked at the method, not just at the container. It is intentionally conservative — it reports only what it can prove from the source text, because a false "unsupported" would train players to ignore the warning.

4. Know which generation you are on

SMLN.whenReady((api) => {
  if (SMLN.api.generation === 'legacy') {
    // 0.5.x: state is bound for you, v1 names still work
  }
  SMLN.sandkit   // the raw, unadapted object, if you really need it
})

Unknown methods always pass through untranslated, so the adapter can never be the reason a call is unavailable — if the build has it under that name, you can call it.

5. Survive a game update

  • Anchor patches on authored strings. Never on ie.FH, never on a module id, never on a byte offset.
  • Declare expect on every patch. Zero matches fails; more than expected also fails, which is what stops a silently-ambiguous pattern from corrupting the bundle in several places at once.
  • Read content from the runtime, not from a table you copied. Element ids and resource fields shift between builds; api is always current.
  • Guard every optional namespace with ?. or an explicit check, so a missing feature costs you one feature.
  • Implement onDispose so hot reload can reclaim your listeners, timers and handlers instead of leaking them.
  • Run the self-test after a game update — node tools/selftest.js names any anchor that stopped resolving.

Three mod formats exist and SandLoader loads all three. They share a manifest filename, so they are told apart by which key is present — never by guessing.

Writing something new? Use SMLN — it has the permissions model, private storage and hot reload. Publishing to the Workshop? Use the official format, which the game loads on its own. Fluxloader is for compatibility with the mods that already exist.

Content bridges, behaviour does not

This one distinction explains most of what people see with older mods.

Content — elements, soils, machines, tech nodes — is captured as the mod registers it, translated into the shape the current build expects, and handed to the game's own registries. That path survives game updates, because it hangs off the API rather than off text in a bundle.

Behaviour lives in patches, and a patch needs its anchor text to still occur in the build. Many older mods were written against older Sandustry versions where it no longer does. On 0.5.6 not one of corelib's own patches still matches, which is precisely why its content is bridged instead.

So an older mod's machine can appear in the build inventory, place correctly, and still do nothing — the definition registered, the logic did not. Every skipped patch is named in the log with the reason.

What the game itself cannot do

One limit here is the game's, not the loader's. Sandustry 0.5.6 contains no function for registering upgrades anywhere in its bundle, so no loader can add one. A mod declaring them loads fine and SandLoader says plainly in the log that those entries could not be registered, rather than failing quietly. Recipes were in the same position until 0.5.6 added a registry with nine machine categories; corelib's four recipe kinds are now translated onto three of them, and contact recipes — element meets element — are reported one by one, because this build gives them no machine id.

Registries are per-thread

The simulation runs across 18 worker threads, each holding its own copy of the element registry. Writing into a registry object by hand reaches none of them — only the game's own registration path reaches all. This is why a hand-mutated element shows up in the inventory and then throws when you spawn it.

  • Test on the vanilla branch before publishing. A mod verified only on the experimental modded branch is verified against an API your players are not running.

Version resistance

SandLoader records a fingerprint of the installation — version, app.asar size and mtime. When any of it moves, the next launch re-reads the renderer bundle and re-resolves every hook before serving a single file. An unchanged install pays nothing; a changed one costs about 50 ms.

  1. Anchors, never offsets. Patches match authored strings ("game:ready"), never module ids or minified names.
  2. Ambiguity is an error. Every patch declares its expected match count. Zero fails; more than expected also fails, because a pattern that silently became ambiguous would corrupt the bundle in several places at once.
  3. All or nothing. A failed required patch aborts and serves the file untouched. A broken loader must not become a broken game.
  4. Runtime over static. Element ids, resource fields and API surfaces are read from the running game; the tables in src/game/enums.js are fallbacks.
  5. Drift detection. tools/selftest.js reports which hooks still resolve, before anyone launches.
What it cannot do

It cannot invent a hook. If the game removes "game:ready" outright, no scan finds a semantic replacement, and guessing would be worse than failing — SandLoader would patch a place nobody chose. In that case it reports where the literal used to be, serves the file unmodified, and the game still starts.

Limitations

An honest list of what is not built yet.

  • Upgrades cannot be registered. Sandustry 0.5.6 has no upgrade registration function anywhere in its bundle, so no loader can add one. A mod declaring upgrades loads; the entries are reported as unregistered rather than silently dropped.
  • Contact recipes cannot be registered. 0.5.6's recipe registry covers nine machine categories, and element-meets-element reactions have no machine id among them. Every other recipe kind registers; contacts are reported one by one.
  • Fluxloader worker mods are translated, not run. SandLoader's own worker mods get the simulation worker's Sandkit through SMLN.whenWorkerReady(). A Fluxloader worker mod does not: corelib's worker half is built from a patch against a bundle chunk 0.5.6 no longer emits, so SandLoader publishes corelib and fluxloaderAPI itself with the calls the bundled mods make reimplemented, and reports what has no equivalent.
  • A dialogue beat has not been seen on screen. The story half of the mission and story SDK registers into the game's own tables and holds its ordering, but reaching a mod's beat needs play up to a factory rank nobody has reached yet. The mission half has been watched completing in the running game.
  • A custom map reloaded from a save gets the vanilla flight ceiling. The scaled no-fly strip keys off custom_map= in the game’s URL, which is the only record that a world is a custom map. Reloading one through the game’s save system brings it back under load=, and there is no state-side signal to tell it apart from the vanilla world, so the fixed 600-pixel strip applies again. Documented, not fixed.
  • The wall layer’s encoding is unverified. Its decoder was never found in the bundle, so the map editor offers a free colour and a live count against the 254-value ceiling, and invents no meaning for what those colours look like in the world.
  • Renderer hot reload is partial by nature. SandLoader reclaims what it handed out — listeners, timers, messaging handlers, recorded registrations. A mod that monkey-patched a game function in place stays patched until the window reloads, and the UI says which stage actually happened.

Frequently asked

The questions that come up before people install, answered directly.

Does this modify my game files?

No. Not one byte. Patching happens in memory as files are served to the renderer.

Will Steam file verification flag it?

It depends on the build. Up to 0.5.5 SandLoader lived in the Workshop content folder and nothing in the game folder changed. Sandustry 0.5.6 removed that loader slot, so SandLoader renames app.asar aside and puts its own directory in its place — no file's content is modified, but Verify integrity of game files does undo the attach. Running node install.js --repair puts the pieces back.

What about GOG?

Supported. Since GOG builds never scan for a loader, SandLoader adds its own resources/app/ directory — three new files beside the untouched app.asar. Electron already searches for app before app.asar, so it loads first and hands control straight back to the real game. No original file is modified, and --uninstall removes the directory again.

Why not Microsoft Store or Game Pass?

That package is ACL-protected and signature-verified. There is no file we are allowed to add, and forcing one would mean modifying the game — so it is reported as unsupported instead of half-working.

Does it work on the experimental / modded branch?

No — SandLoader supports the vanilla branch only, which is Steam's default public branch.

The two branches ship different generations of Sandustry's modding API: vanilla has the legacy Sandkit surface, the modded branch has Sandkit v1 with namespaces vanilla does not have. SandLoader is built and verified against the vanilla generation, and translates v1 call names onto it so mods are written once — but it does not run on the modded branch.

To switch back: right-click Sandustry in Steam → Properties → Betas → select None. Installing on the experimental branch is not blocked, but nothing about it is verified — patch anchors may not resolve, and the loader will report what failed rather than pretend it worked.

Can this get me banned?

Sandustry is single-player and ships no anti-cheat. There is nothing to ban.

Will a game update break it?

Possibly — and it will tell you. Hooks are anchored on strings from the game's source rather than on positions or minified names, so they usually survive. When one doesn't, the loader serves the game unpatched instead of half-patched: you can still play, just without mods, and tools/selftest.js names the break.

Do I need to reinstall after editing SandLoader's code?

No. Just restart the game.

Is it safe to install a random mod ZIP?

A mod is arbitrary code with full Node access, exactly like this loader. The installer rejects archives without a valid manifest and refuses any that try to write outside the mods folder, but it cannot judge what the code does. Treat mods like any other software you install.

Does it work with Fluxloader mods?

Yes, unmodified. SandLoader reads their modinfo.json, runs all three entrypoints, provides the fluxloaderAPI global, translates their patches onto its own patch engine, and persists their config. It shares no code with that project — it answers the same interface.

Library mods work too: corelib and the mods that build on it load in dependency order and share one global scope, so a mod can call corelib.elements.registerElement(…) exactly as it does under Fluxloader.

With one honest caveat, because it decides what actually happens in game: content carries across, behaviour does not always. A mod's elements, soils, machines and tech nodes are translated and handed to the game's own registries, so they appear and work. A mod's patches need anchor text that still occurs in the current bundle — and many older mods were written against older Sandustry builds where that text has since changed. On 0.5.6, none of corelib's own patches still match, which is exactly why SandLoader bridges its content instead of relying on them.

The practical shape of that: a machine from an older mod shows up in the build inventory and can be placed, but may do nothing until the mod itself is updated. The log names every patch that failed and why. See the Fluxloader section for the detail.

Why does it need Node.js?

Only to run the installer, which locates your game and writes the attach point. The loader itself runs inside the game's own Electron process and needs nothing extra at play time.

SandLoader

A mod loader for Sandustry that never rewrites a game file. MIT licensed, no dependencies, no build step.
